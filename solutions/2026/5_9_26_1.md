# Automation Testing — From Tester to Software Engineer

## Let’s Begin with a Story...

Imagine that Transflower is building a new product — an **Insurance Management System**. In this product, a customer can register, log in, view policies, pay premiums, raise claims, and track claim status. Now someone in the team says: “My job is testing.” Another person says:  “My job is writing code.” But what does a **Software Engineer** say **“My responsibility is to make sure the product works correctly and solves the intended problem.”** That is the mindset we need to develop.

# 1. Product First, Testing Second

When we build a product, our first question should not be: “What test case should I write?” Our first question should be: **“What problem is our product solving?”** For example, consider our Insurance Application.

A customer should be able to:
* Register
* Log in
* Purchase a policy
* View policy details
* Pay premiums
* Raise a claim
* Check claim status

Now testing naturally begins. We start asking:

- **Can a valid customer log in?**
- **Can an invalid customer be prevented from logging in?**
- **Can a registered customer view their policies?**

Testing comes from understanding the product.

# 2. Understand the Testing Environment

Before starting Automation Testing, we need to understand the environment. Suppose our application looks like this:

```text
Frontend
   ↓
React / Angular
   ↓
ASP.NET Core Web API
   ↓
MySQL
```

And our environments look like:

```text
Developer Machine
        ↓
Test Environment
        ↓
QA / Staging Environment
        ↓
Production Environment
```

Every environment has a different purpose.

### Developer Environment : Developers build and test features.
### Test Environment : Manual and automated tests are executed here.
### QA / Staging Environment : The application is validated in an environment that is close to production.
### Production ; Real customers use the application.

Therefore, an Automation Engineer should not know only Selenium or Playwright. The engineer should also understand:

> **Where is the application running?
> Where is the API?
> Where is the database?
> Where is the test data?
> Where are the logs?
> How does authentication work?**

That is engineering.

# 3. What is Automation Testing?

Suppose we need to perform the following test 100 times every day:

```text
Open application
      ↓
Enter username
      ↓
Enter password
      ↓
Click Login
      ↓
Verify Dashboard
```

Doing this manually every time is inefficient. So we write a program that performs these steps automatically. That program is an:  **Automation Script**

Conceptually:

```text
Test Case
   ↓
Automation Script
   ↓
Browser
   ↓
Application
   ↓
Result
```

But remember:  **Writing an automation script is not the same as Automation Testing.** Automation Testing is a complete engineering process.

 
# 4. Manual Testing + Automation Testing

We should not treat these as competitors.

### Manual Testing

A human thinks, explores, observes, and discovers unexpected behavior.

### Automation Testing

A machine repeatedly executes predefined scenarios.

For example:

```text
Manual Testing
    ↓
Explore
    ↓
Understand
    ↓
Discover Scenarios
    ↓
Create Test Cases
```

Then:

```text
Automation Testing
    ↓
Select Repeatable Scenarios
    ↓
Create Automation Scripts
    ↓
Execute
    ↓
Report Results
```

Therefore: **Automation does not simply replace Manual Testing.**  The purpose of automation is: **To automate repeatable work and free engineers to focus on higher-value thinking.**

 

# 5. The Most Important Word — MVP

Now we come to a very powerful concept:

## MVP — Minimum Viable Product

We cannot build and test the entire product in one day. We build the product incrementally through small, usable pieces. Suppose we have an Insurance Application. Our first MVP could be:

### MVP-1 — Authentication

Requirement: **Only a valid user should be allowed to enter the system.**  Now we break this requirement into smaller scenarios:

```text
MVP-1
Authentication
    │
    ├── User Registration
    ├── Valid Login
    ├── Invalid Login
    ├── Logout
    └── Session Validation
```

Now our testing scope becomes clear.

# 7. Product Immaturity → Product Maturity

A new product is immature in the beginning. The journey looks something like this:

```text
Idea
 ↓

 ↓

 ↓

 ↓

 ↓
```

Automation Testing plays an important role in this maturity journey. But remember: **Product maturity does not come simply from increasing the number of automation scripts.**

Maturity comes from:

```text

       +

       +

       +

```


# 8. Change the Mindset — “I Am a Tester”

This is one of the most important mentoring lessons.

❌ Limited mindset:

> “I am a tester. My job is only to write test cases.”

Another limited mindset is:

> “I am a developer. Testing is not my responsibility.”

Both are incomplete ways of thinking.

Our mindset should be:

> **“I am a Software Engineer.”**

A Software Engineer can understand requirements. A Software Engineer can understand architecture. A Software Engineer can write code. A Software Engineer can understand databases. A Software Engineer can perform testing. A Software Engineer can automate tests. A Software Engineer can investigate production issues. That is the engineering mindset.

# 9. Software Engineering Has Multiple Responsibilities

In a product organization, there may be different roles:

```text
Software Engineer
       │
       ├── Developer
       ├── Manual Test Engineer
       ├── Automation Engineer
       ├── QA Engineer
       ├── DevOps Engineer
       └── SDET
```

These are different **job roles**. But engineering mindset is different. A good Software Engineer should understand what these different roles are doing and how their work affects the product.
 
# 10. Let's Take Authentication as an Example

Now let's build our first MVP.

### Requirement

> **Only a valid user should be allowed to enter the system.**

Now we analyse the requirement.

### User Registration

```text
Customer
   ↓
Enter Personal Details
   ↓
Validate Data
   ↓
Create Account
```

Now we ask questions:

* Is the username unique?
* Is the email valid?
* What is the password policy?
* Which fields are mandatory?
* What happens when invalid data is entered?
* What happens when a duplicate user is registered?

This is **analysis**.


# 11. Now Create Test Scenarios

For Registration:

```text
TC01 → Valid registration
TC02 → Duplicate email
TC03 → Invalid email
TC04 → Empty mandatory field
TC05 → Invalid password
TC06 → Password confirmation mismatch
```

For Login:

```text
TC07 → Valid username + valid password
TC08 → Valid username + invalid password
TC09 → Invalid username
TC10 → Empty username
TC11 → Empty password
TC12 → Locked user login
```

Now the Automation Engineer has meaningful scenarios to automate.

# 12. Where Does the Automation Script Come In?

Now we create the automation.

Conceptually:

```text
Test Case
    ↓
Automation Script
    ↓
Browser
    ↓
Login Page
    ↓
Enter Credentials
    ↓
Click Login
    ↓
Verify Result
```

For example:

```text
Given
    the customer is registered

When
    the customer enters valid credentials

And
    the customer clicks Login

Then
    the customer should see the Dashboard
```

This is more than just a script.

It is: **Automated verification of business behavior.**


# 13. Now Where Does AI Come In?

Today, one of the most interesting questions is: **How is AI changing Automation Testing?**

AI can assist in many activities:

```text
Requirement
     ↓
AI
     ↓
Test Scenario Suggestions
     ↓
Test Cases
     ↓
Automation Code
     ↓
Execution
     ↓
Failure Analysis
```

AI can help with:

* Test case generation
* Test data generation
* Automation script generation
* Locator suggestions
* API test generation
* Test failure analysis
* Log analysis
* Regression test selection
* Test documentation
* Bug summarization

But there is one important rule: **AI does not eliminate the responsibility of the Test Engineer or Software Engineer.** AI can provide suggestions. The engineer must validate them.

# 14. AI + Automation — The New Engineering Loop

### Traditional Approach

```text
Requirement
     ↓
Human writes test cases
     ↓
Human writes automation
     ↓
Human executes tests
     ↓
Human analyses failures
```

### AI-Assisted Approach

```text
Requirement
     ↓
AI assists with analysis
     ↓
AI suggests scenarios
     ↓
Engineer reviews
     ↓
AI assists with automation
     ↓
Engineer validates
     ↓
Automation executes
     ↓
AI assists with failure analysis
     ↓
Engineer makes final decision
```

Therefore:  **AI makes execution faster; it does not replace engineering judgment.**

# 17. What Is Our Real Goal?

Our goal is not: “I learned Selenium.”  Or:  “I learned Playwright.” Or:  “I can write 500 automation scripts.”
The real goal is: **“I can understand a software product, identify its risks, design meaningful tests, and intelligently automate those tests.”** That is the **Software Engineering mindset**.
